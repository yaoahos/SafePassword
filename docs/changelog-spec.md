# 更新日志规范（可复用到其它 App）

本项目 App 内「更新日志」页面的完整口径。目标是三处一致：**应用内更新日志、README 版本记录、GitHub Release 正文**——同一份文案，不改写、不增删。

---

## 一、数据从哪来

| 来源 | 位置 | 用途 |
| --- | --- | --- |
| 内置日志 | `apps/android/src/main/assets/updateLog.md` | 离线可看，含尚未发布的版本 |
| 远端日志 | GitHub `releases`（取 `body`） | 已发布版本，最多取 50 个 |
| 二者合并 | 按版本号降序 | 未发布的本地条目自然排最前 |

三者使用**同一个 Markdown 子集**，所以 GitHub 正文可以直接被 App 解析显示。

---

## 二、文本格式

```markdown
**2026/11/05 · 1.0.3**
- 修复 收藏、删除或改名后列表未回到顶部
- 优化 条目默认图标改为 17 色色板，同名条目跨端同色
- 新增 启动时检查更新，可在关于页关闭

**2026/11/04 · 1.0.2**
- 修复 检查更新偶发失败，并区分限流与网络错误
```

规则：

1. **版本标题**一行一个，必须用 `**` 包裹，形如 `**日期 · 版本号**`。
   - 日期 `YYYY/MM/DD`，用斜杠；补零。
   - 分隔符用中点 `·`（两侧各一个空格）。
   - 版本号不带 `v`。
   - 整行长度控制在 4–40 字符。
2. **条目**以 `- ` 开头，每条一行，`- ` 之后是「动词 + 空格 + 描述」。
3. 动词只用五类：**新增 / 优化 / 修复 / 变更 / 安全**。
4. 版本之间空一行；文件末尾不要多余空行。

---

## 三、内容要求

**写什么**

- 用户能感知的结果：多了什么功能、哪里变快了、什么毛病没了。
- 一条只讲一件事，一句话说完，建议 ≤ 40 个汉字。
- 涉及具体对象时点名，例如「收藏、删除或改名后列表未回到顶部」。

**不写什么**

- 发布信息：包名、`versionCode`/`versionName`、系统要求、适用版本、下载地址、文件大小、SHA/MD5、签名、校验值、安装说明、更新日期。
- 实现细节：类名、函数名、框架名、接口名、重构手法。
- 客套话：「本次更新优化了用户体验」「欢迎反馈」这类空话。
- 图片、表格、`>` 引用块、二级标题、`---` 分隔线。
- 迁移通知（「需先卸载旧版」这类）放 README 或 Release 之外的说明里，不进日志。

**好 / 坏对比**

| 坏 | 好 |
| --- | --- |
| 优化了数据库的序列化方式，减少体积 | 优化 密码库文件体积大幅缩小，同步更快 |
| 修复 bug | 修复 云端删除密码库后，另一端仍停留在旧列表 |
| 新增：支持导出；新增：支持导入；新增：支持备份 | 拆成三条，每条只讲一件事 |

---

## 四、解析规则（容错）

- 标题识别：`**...**` 包裹，且内容匹配
  `^(\d{4}[-/]\d{1,2}[-/]\d{1,2})(?:\s*[·\-—]\s*|\s+)?(v?\d+(?:\.\d+)*)?$`
  —— 因此 `2026/11/05 · 1.0.3`、`2026-11-05 1.0.3`、`2026/11/05` 都能解析。
- 匹配不上时，整行当作日期、版本留空（不丢内容）。
- 只把 `- ` 开头的行当条目，其余行全部忽略（适配 GitHub 正文里的各种附加内容）。
- 版本标题之后必须至少有一条目，否则该版本丢弃。

## 五、展示规则

### 5.1 整体结构

弹窗从上到下只有四块：

```
┌─ 更新日志 ──────────────────────┐   ← 标题（对话框 title）
│ 2026/11/05    v1.0.3            │   ← 版本标题（每个版本一条）
│ · 修复 收藏后列表未回到顶部      │   ← 条目，完整列出
│ · 优化 默认图标改为 17 色色板    │
│ ─────────────────────────────── │   ← 版本之间的分隔线
│ 2026/11/04    v1.0.2            │
│ · 修复 检查更新偶发失败          │
│                                  │
│ 查看更早的版本                   │   ← 列表末尾的入口
└──────────────────────────────────┘
│                                    关闭 │   ← 对话框按钮
```

### 5.2 版本标题

- 内容：`日期` + **四个空格** + `v版本号`，例如 `2026/11/05    v1.0.3`
- 只有日期时只显示日期；只有版本时只显示 `v版本号`；两者都缺时显示「更新」
- 样式：`titleSmall`（比正文大一号、加粗），主题默认文字色

### 5.3 版本之间必须有分隔线

- **除第一个版本外，每个版本前都要插一条分隔线**：`HorizontalDivider`，粗细 1dp
- 分隔线上下各留 12dp 空白，视觉上把两版内容分开
- 不要用空行代替分隔线——纯空行在长列表里分不清是换版还是条目间距

### 5.4 条目

- 每条一行，显示时前缀「· 」（中点 + 空格）
- 样式：`bodySmall`，主题默认文字色
- 条目之间 3dp 间距
- **每一版的全部条目都显示**，不截前几条；单条超 80 字时截成 78 字加 `…`
- 某版本条目全被过滤掉时，该版本下显示「问题修复与稳定性优化。」兜底，不要留空

### 5.5 列表末尾的「查看更早的版本」

- 位置：滚动列表的**最底部**，在所有版本之后
- 形态：文字按钮（`TextButton`），文案固定为「查看更早的版本」
- 动作：用系统浏览器打开**本项目的 GitHub Releases 页面**，例如
  `https://github.com/yaoahos/SafePassword/releases`
  不要硬编码到某个具体 tag，始终用仓库的 `/releases` 列表页
- 显示条件：只在至少有一个版本时显示；列表为空或加载中时隐藏
- 作用：App 内只展示最近 50 个版本，更早的让用户去网页看

### 5.6 尺寸与滚动

- 弹窗内容区最大高度 420dp，超出后在内部滚动（不要整页滚动）
- 分隔线、间距都算在滚动区域内

### 5.7 空态与加载态

- 加载中且无数据：「正在获取更新日志…」
- 加载完成但无数据：「暂无更新日志。」

### 5.8 数量

- 最多列 50 个版本，按版本号降序（见第七节）

## 六、过滤规则

条目先做 Markdown 清洗：去掉行首 `- ` `* ` `+ ` `• `，去掉 `**` 与反引号，去首尾空白，空行丢弃。

再剔除以下噪声（包含任一关键词即丢弃）：

```
包名、versionCode、versionName、版本号、系统要求、适用系统、适用版本、
安装说明、安装包、下载地址、文件大小、SHA、MD5、签名、校验值、更新于
```

再丢弃整行属于以下形态的：

- 以 `#` `>` `|` `![` `---` 开头（标题、引用、表格、图片、分隔线）
- 整行只有日期：`\d{4}[/-]\d{1,2}[/-]\d{1,2}`
- 整行是「日期 + 版本号」标题：`^\d{4}[/-]\d{1,2}[/-]\d{1,2}\s*[·\-—]?\s*v?\d+(?:\.\d+)*$`

> 最后两条是为了兼容「把整段日志塞进 Release 正文」的写法：正文自带的标题行不该在对话框里重复出现。

---

## 七、排序与比较

- 版本号比较按数值分段：拆 `1.0.10` → `[1,0,10]`，逐段比较，短的一侧补 0。
- 合并本地与远端后按版本号**降序**，不要按字符串排序（`1.0.10` 会排到 `1.0.9` 前面去）。
- 判断「有没有新版本」同样用分段比较，而不是字符串比较。

---

## 八、移植到新项目的最小清单

1. 数据类：`ReleaseNote(version: String, date: String, notes: String)`。
2. 解析器：读 Markdown → `List<ReleaseNote>`（上面第四节）。
3. 过滤器：条目清洗 + 噪声剔除（第六节）。
4. 排序器：版本号分段比较（第七节）。
5. 对话框：标题「更新日志」+ 可滚动列表 + 「查看更早的版本」+「关闭」。
6. 入口：设置/关于页一行「更新日志」，副标题可显示当前版本号。
7. 数据源二选一或都接：内置 `assets/updateLog.md`（离线优先）、远端 Release 正文（自动累积历史）。

---

## 九、发布时的一致性检查

发版前确认三处文案完全一致：

- [ ] `apps/android/src/main/assets/updateLog.md` 新增一个版本标题 + 条目
- [ ] `README.md` 的「版本记录」新增同样内容
- [ ] GitHub Release 正文用同样内容（标题只写版本号，正文不写大小/哈希/包名）

> 曾经出现过「台账更新了但 Release 正文没改」的情况，导致 App 内显示的条目比 Gallery 上少。用同一份文案复制粘贴可以避免。
